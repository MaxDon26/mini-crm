# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Тестовое задание: мини-CRM «Объекты и задачи» для строительной компании. Стек из ТЗ: React + TypeScript, Supabase.
Оценивают логику, защиту данных и понимание сделанного; дизайн не оценивают. На работу заложено 2–3 часа.

## Команды

- `npm run dev`, `npm run build`, `npm run typecheck`, `npm run lint`.
- `npm run db:start`, `npm run db:stop`, `npm run db:reset` (пересоздаёт локальную базу из миграций), `npm run db:types`. Нужен
  запущенный Docker Desktop.
- `npm run test:db` (локальная Supabase должна быть запущена), `npm run test:unit`, `npm run test:e2e`.
- Один файл тестов: `node --test tests/db/access.test.ts`.
- В npm, GitHub и при `npm run test:e2e` очищать `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`: иначе Playwright не дождётся сайта.
- В heredoc Git Bash обратные слэши могут теряться: файлы с `\` и `\u` записывать инструментами `Write` и `Edit`.

## Правила предметной области (ТЗ, не менять)

Роли:
- Постановщик: создаёт, редактирует, удаляет объекты и задачи; назначает исполнителя; принимает или возвращает на
  доработку; видит всё.
- Исполнитель: видит только свои задачи и объекты, где они у него есть; берёт в работу и отправляет на проверку.

Переходы статусов (другие запрещены):

| Из | В | Кто | Условие |
|---|---|---|---|
| — | Новая | постановщик | при создании задачи |
| Новая | В работе | назначенный исполнитель | — |
| В работе | На проверке | назначенный исполнитель | — |
| На проверке | Принята | постановщик | — |
| На проверке | На доработке | постановщик | комментарий обязателен |
| На доработке | В работе | назначенный исполнитель | — |

История: каждая смена статуса — кто, когда, откуда, куда, комментарий (если есть); видна обеим ролям в карточке задачи.

Экраны: вход, список объектов, карточка объекта, карточка задачи, «Мои задачи» для исполнителя. Интерфейс показывает только
действия, доступные текущему пользователю в текущем статусе.

## Безопасность (ТЗ, раздел 3)

Правила обязаны работать при прямом обращении к Supabase в обход интерфейса:
1. Права закрыты в базе (RLS), а не только скрыты в интерфейсе.
2. Исполнитель не может прочитать или изменить чужие задачи.
3. Запрещённый переход статуса не проходит даже при ручном запросе: проверка на стороне базы.
4. Историю статусов нельзя подделать, изменить или удалить через API.
5. Открытая регистрация отключена.
6. `service_role` и другие секретные ключи не попадают во фронтенд и в репозиторий.

Особенности этого проекта:
- Локальные файлы с учётными данными в git не добавлять и не открывать, значения нигде не повторять (см. `.gitignore`).
- Пароли тестовых пользователей не класть в миграции и репозиторий.

## Устройство (решения, подробности в документе задачи)

- **Удаление** только скрывает: отметка «удалена», кто и когда. Удалённое база не отдаёт через API никому, в том числе
  постановщику. Настоящего удаления через API, экрана удалённых и восстановления нет.
- **Роль** хранится в таблице профилей, пользователь её не меняет. Профиль создаётся автоматически с ролью «исполнитель».
- **Статус** меняется только через одно действие базы: номер задачи, статус, который видел пользователь, новый статус,
  комментарий. Через API напрямую поле не изменить, исполнителю закрыта любая прямая правка задач.
- **Функции с повышенными правами** лежат в закрытой схеме, сайт вызывает тонкие обёртки (статус, удаление задачи, удаление
  объекта). Функции сначала блокируют строку, затем проверяют права; на чужую задачу отвечают «Задача не найдена».
- **Роль проверяется точным совпадением**, пустое значение даёт отказ; сравнения старых и новых значений учитывают пустые.
- **Правка задачи постановщиком** обычная: название, описание, исполнитель, кроме принятых. Объект задачи не меняется (Р28). Отдельный триггер следит
  за этими полями и пишет смену исполнителя в историю.
- **История** пишется только базой. Триггер запрещает её изменение и удаление, `service_role` прав на наши таблицы не получает.
- **Права** на таблицы и функции прописываются в миграциях явно: автоматической выдачи на новых проектах Supabase нет.
- **Тестовые данные** заводятся скриптом с публичным ключом, под тестовыми пользователями и настоящими действиями. Проверять
  права можно только через API с токеном пользователя: `postgres` в SQL-редакторе обходит RLS.
- **Код сайта:** `src/app` (маршруты, экраны), `src/features/{auth,objects,tasks}`, `src/shared`. Импорт только в одну
  сторону: `shared` → `features` → `app`, разделы друг друга не импортируют. Запросы к базе только в `api.ts` разделов.
- **Кнопки** сайт выбирает по таблице в `features/tasks/statuses.ts`, решает всё равно база. Проверочный сценарий сравнивает
  эту таблицу с ответами базы.
- **Инструменты сайта:** Vite, React Router, TanStack Query, Mantine. Redux, Zustand и отдельной библиотеки проверки форм нет.
- **Комментарии** только «почему», на русском, имена в коде на английском. В SQL шапка у каждого правила, функции и триггера:
  что защищает и какой пункт ТЗ или решение. Стиль кода — раздел 3.6 документа задачи.
- **Тесты обязательны:** защита базы через API с токеном каждого участника, логика сайта, сверка кнопок с базой (`node:test`),
  один сквозной сценарий (Playwright). Тесты защиты пишем вместе с каждой миграцией. Запускаются на локальной Supabase (CLI и
  Docker), база пересоздаётся из миграций; на сдаваемой базе тесты не гоняем. Сценарии — раздел 4 документа задачи.
- **Сетевые запросы** всегда видны: скелетоны при загрузке, индикатор и блокировка кнопок при действиях, «Повторить» при
  ошибке. Состояния — общими компонентами из `shared/ui` (раздел 3.7 документа задачи).
