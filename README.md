# Мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании: постановщики ставят задачи по объектам (стройкам), исполнители выполняют их и
отдают на проверку. React, TypeScript, Supabase.

Сайт: https://mini-crm-sable-two.vercel.app — доступы передаются вместе со ссылкой.

## Коротко для руководителя

**Как устроено.** Система состоит из двух частей: сайта, который видит человек, и базы данных — хранилища, где лежат объекты,
задачи и их история. База находится в облачном сервисе Supabase. Сайт сам ничего не решает: он только показывает данные и
кнопки. Все правила — кто что видит и что может сделать — проверяет сама база при каждом обращении.

**Как защищены данные.** Каждое обращение к базе приходит с «пропуском» вошедшего пользователя, и база по нему решает, что
отдать и что разрешить. Поэтому правила работают, даже если обратиться к базе в обход сайта, например специальной программой:
ответ будет тот же, что и на сайте. Смена статуса задачи проходит только по разрешённым шагам из ТЗ. Историю изменений пишет
сама база, поправить или стереть её нельзя никому. Удаление скрывает объект или задачу, но история остаётся. Регистрация
закрыта: пользователей заводит администратор. Секретных ключей нет ни на сайте, ни в коде.

**Чего не может исполнитель.** Видеть чужие задачи и объекты, где у него нет задач. Менять название, описание и исполнителя
задачи. Принимать работу или возвращать её на доработку. Перескакивать через статусы. Править или удалять историю. Удалять
задачи и объекты. Назначить себе роль постановщика.

**Как это проверено.** 525 автоматических проверок: 397 из них обращаются к базе напрямую от имени гостя, исполнителей и
постановщиков и пытаются обойти правила, 114 проверяют логику сайта, 14 проходят сценарии в настоящем браузере.

## Как устроено

- `supabase/migrations` — вся защита: таблицы, правила доступа (RLS), права на колонки, функции и триггеры. У каждого правила
  в шапке написано, что оно защищает и на какой пункт ТЗ или решение опирается.
- Статус меняется только функцией `change_task_status`: она блокирует строку, проверяет доступ, ожидаемый статус, переход и
  комментарий, затем пишет историю. Удаление — функции `delete_task` и `delete_object`. Логика лежит в закрытой схеме
  `private`, сайт вызывает тонкие обёртки без повышенных прав.
- `src/app` — маршруты и экраны, `src/features/{auth,objects,tasks}` — разделы, `src/shared` — общий код. Импорт идёт только
  в одну сторону (`shared` → `features` → `app`), запросы к базе только в файлах `api.ts`; это проверяет ESLint.
- `tests/db` — защита через API с токеном каждого участника, `tests/unit` — логика сайта, `tests/e2e` — браузер (Playwright).
- Решения, спецификация и сценарии проверки — `docs/goals/mini-crm.md`.

## Запуск локально

Нужны Node.js 22.18 или новее и запущенный Docker Desktop.

```bash
npm install
npm run db:start      # локальная Supabase в Docker, миграции применяются сами
npm run local:setup   # пишет .env.local и заводит 4 тестовых пользователей с ролями
npm run seed          # тестовые объекты и задачи настоящими действиями пользователей
npm run dev
```

Пароли тестовых пользователей — в `.env.local` (файл вне git). Пересоздать базу из миграций: `npm run db:reset`, затем
снова `npm run local:setup`.

## Тесты

```bash
npm run test:db     # нужна запущенная локальная Supabase
npm run test:unit
npm run test:e2e    # нужны .env.local и тестовые пользователи (npm run local:setup)
npm run typecheck && npm run lint
```

Один файл: `node --test tests/db/access.test.ts`. Тесты базы заводят свои данные и не мешают друг другу.

## Развёртывание

1. Создать проект Supabase с выключенным «Automatically expose new tables»: права выдают миграции.
2. В настройках входа выключить регистрацию и анонимный вход.
3. Применить миграции: `npx supabase link --project-ref <ref>`, затем `npx supabase db push --remote`.
4. Создать пользователей в панели (Authentication → Users, с подтверждением), затем назначить роли и имена:

   ```sql
   update public.profiles p
   set role = v.role::public.app_role, full_name = v.full_name
   from (values ('anna@example.com', 'manager', 'Анна Петрова')) as v(email, role, full_name)
   join auth.users u on u.email = v.email
   where p.id = u.id;
   ```

5. Тестовые данные: заполнить `.env.cloud.local` по образцу `.env.example` и выполнить `npm run seed:cloud`.
6. Сайт: любой статический хостинг со сборкой `npm run build`, папка `dist`, переменные `VITE_SUPABASE_URL` и
   `VITE_SUPABASE_KEY` (публичный ключ). Для Vercel прямые ссылки на страницы настроены в `vercel.json`.

## Решения и допущения

Полный список с причинами — `docs/goals/mini-crm.md`, разделы 2 и 2.3.

- Удаление только скрывает задачи и объекты: строки остаются, чтобы история не пропадала. Через API удалённое не видит никто.
- Удаление объекта скрывает все его задачи, принятую задачу удалить можно.
- Объект задачи задаётся при создании и не меняется. Принятую задачу нельзя править.
- Исполнитель при создании необязателен. Снять его можно только у новой задачи, сменить — в любом статусе, кроме «Принята»;
  смена исполнителя пишется в историю.
- Принять или вернуть задачу может любой постановщик. Комментарий можно оставить при любом переходе, обязателен он только
  при возврате.
- У пользователя одна роль. Новый пользователь получает роль «исполнитель», постановщика назначает администратор.
- Исполнитель видит имена только тех, кто связан с его задачами.
- В списке объектов у постановщика есть число задач на проверке — дополнение сверх ТЗ.
- Защита действует для всех, кто обращается через API. Владелец проекта в панели Supabase вне её.
- Известные ограничения: вход по коду на почту отвечает по-разному на существующий и несуществующий email; примерный
  подсчёт строк показывает порядок размера таблиц; проверка паролей по базе утёкших в Supabase выключена.

## Что не успели

- Тестов отдельных компонентов нет: логика вынесена из компонентов и проверена юнит-тестами и браузером.
- Сайт выкладывается командой Vercel CLI, автоматической выкладки при каждом изменении в репозитории нет.
