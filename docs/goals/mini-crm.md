# Задача: мини-CRM «Объекты и задачи»

**Статус:** в работе, согласовано 2026-11-05. Блоки 1–9 решены (1–4 сверены независимой проверкой на бумаге). Ход работы — раздел 5.1.

Требования — файл `Тестовое задание мини-CRM «Объекты и задачи».docx.pdf`. Ссылки вида «ТЗ п. 3.4» ведут на его разделы.
Этот документ их не заменяет: он фиксирует решения там, где ТЗ не даёт однозначного ответа.

## 1. Постановка

**Зачем.** Небольшая CRM для строительной компании: постановщики ставят задачи по объектам (стройкам), исполнители
выполняют их и отдают на проверку. Оценивают логику, защиту данных и понимание сделанного; дизайн не оценивают.

**Что должно получиться.** Работающее приложение на React + TypeScript и Supabase: две роли, объекты, задачи с циклом
статусов и историей, 5 экранов. Правила доступа работают и при прямом обращении к Supabase, в обход сайта.

**Что сдаём** (ТЗ п. 4): ссылку на приложение с доступами (минимум один постановщик и два исполнителя, 2–3 объекта, задачи
в разных статусах), репозиторий с миграциями и README, объяснение для руководителя-непрограммиста, список решений и
допущений, а также что не успели.

**Сроки.** На работу заложено 2–3 часа, сдать нужно как можно быстрее. ТЗ просит заранее написать, когда приступаем и когда
планируем сдать: это сообщение отправляется в чат на hh.ru до начала работы.

**Что не входит.** Всё, что перечислено в разделе 3.5.

### 2.2. Предложения без прямого подтверждения

- На сайте есть кнопка выхода, восстановления пароля нет.
- Связь истории с задачей и с пользователем без каскадного удаления: база откажет в настоящем стирании того, на что
  ссылается история.

### 2.3. Что записать в список допущений при сдаче

**Удаление**
- Удаление только скрывает задачи и объекты, строки остаются в базе (отступление от буквы ТЗ п. 2.1). Прямой запрос на
  удаление строки получает отказ: удаление идёт через отдельное действие.
- Удаление объекта скрывает все его задачи, включая принятые. Принятую задачу можно удалить.
- Удалённое и его история не отдаются через API, в том числе постановщику. Посмотреть можно в панели Supabase, там же видно,
  кто и когда удалил. Восстановления нет.

**История**
- Смена исполнителя пишется в историю (дополнение сверх ТЗ п. 2.4). Правки названия, описания и перенос в другой объект не
  пишутся: старое значение не сохраняется.
- В записях показывается текущее название задачи и текущее имя пользователя.

**Задачи и исполнители**
- Принять или вернуть задачу может любой постановщик, а не только автор.
- Комментарий можно оставить при любом переходе, обязателен он только при возврате на доработку.
- Принятую задачу нельзя править (в ТЗ ограничения нет).
- Исполнитель необязателен при создании, снять его можно только у задачи в статусе «Новая». Сменить можно в любом статусе,
  кроме «Принята», и прежний исполнитель сразу теряет доступ к задаче и её истории.
- Назначить можно только пользователя с ролью исполнителя. У пользователя одна роль.
- Обязательны название и адрес объекта, название задачи и её объект. Описание необязательно. Длина текста ограничена.

**Пользователи**
- Новый пользователь автоматически получает роль «исполнитель». Роль меняется вручную в Supabase.
- Если назначенному исполнителю сменить роль на постановщика, его задачи ждут передачи другому, и он может принять свою
  бывшую работу.
- Исполнитель видит имена только причастных к его задачам (в ТЗ о профилях ничего нет).
- Пользователя с профилем нельзя удалить обычным способом, только заблокировать. Неиспользованного можно убрать, сначала удалив его
  профиль через SQL.

**Экраны**
- Столбец «На проверке: N» в списке объектов и задачи на проверке первыми в карточке объекта — дополнение сверх ТЗ п. 2.5.

**Границы защиты и известные ограничения**
- Защита действует для всех, кто обращается через API. Владелец проекта в панели Supabase вне её: статус, отметку и историю
  вручную не правим. Поля задачи в панели не правятся: без текущего пользователя база отказывает. Очистка таблицы истории тоже
  запрещена, начать заново можно только новым проектом.
- Постановщик с устаревшей карточкой может принять работу, которую вернули и сдали заново, пока карточка была открыта.
- Через вход, возможно, можно проверить, существует ли email (поведение Supabase, проверим на проекте).

## 3. Спецификация

Заполнена по блокам 1–6. Настройки и выкладка появятся после блоков 7–8.

### 3.1. Поведение

**Кто что может**

| Данные | Постановщик | Исполнитель |
|---|---|---|
| Объекты | Видит все; создаёт, правит, удаляет | Видит только те, где есть его неудалённые задачи; не меняет |
| Задачи | Видит все; создаёт, удаляет; у непринятых правит название, описание, объект, исполнителя | Видит только свои, в том числе в карточке объекта; меняет только статус по цепочке |
| История | Читает всю; не меняет | Читает по своим задачам; не меняет |
| Профили | Видит все; не меняет | Видит себя и причастных; не меняет |

Удалённое через API не получает никто. Без входа через API недоступно ничего.

**Статусы.** Таблица совпадает с ТЗ п. 2.3, другие переходы запрещены.

| Из статуса | В статус | Кто может | Условие | Как у нас |
|---|---|---|---|---|
| — | Новая | постановщик | при создании задачи | База сама ставит статус «Новая» |
| Новая | В работе | назначенный исполнитель | — | Назначенный пользователь с ролью исполнителя |
| В работе | На проверке | назначенный исполнитель | — | То же |
| На проверке | Принята | постановщик | — | Любой постановщик |
| На проверке | На доработке | постановщик | комментарий обязателен | Любой постановщик, комментарий не пустой |
| На доработке | В работе | назначенный исполнитель | — | Назначенный пользователь с ролью исполнителя |

**История в карточке задачи (пример)**

| Когда | Кто | Что |
|---|---|---|
| 12.11 10:00 | Анна | Создана: Новая, исполнитель не назначен |
| 12.11 10:05 | Анна | Исполнитель: не назначен → Иван |
| 12.11 11:00 | Иван | Новая → В работе |
| 13.11 09:00 | Анна | Исполнитель: Иван → Пётр |
| 13.11 12:00 | Пётр | В работе → На проверке |

Пётр видит всю эту историю. Иван после передачи не видит ни задачу, ни её историю.

**Правила базы**

*Права*
- Роль проверяется в момент действия. Действие разрешено только при точном совпадении роли, пустое значение даёт отказ.
- Права на таблицы и функции прописываем в миграциях явно и выдаём только нужные. `anon` и `service_role` прав на наши
  таблицы не получают. С функций права снимаем и у `public`, и у `anon`.
- Постановщик напрямую создаёт и правит задачу только в полях: название, описание, объект, исполнитель. Объект — название и
  адрес. Автор, дата создания, статус и отметка «удалена» через API напрямую не меняются.
- Функции с повышенными правами закрепляют `search_path`, сначала блокируют строку, затем проверяют права. На чужую задачу
  отвечают «Задача не найдена». Без входа их вызвать нельзя.
- Служебные функции для правил доступа работают только с текущим пользователем, его номер параметром не принимают.

*Смена статуса*
- Статус, который видел пользователь, не совпал с текущим: «Статус уже изменён». Совпал, но такого перехода нет: «Переход
  запрещён». Поэтому при двойном клике или двух одновременных нажатиях проходит только первое действие.
- При возврате на доработку комментарий обязателен. В остальных переходах необязателен (ТЗ п. 2.4: «комментарий (если
  есть)»).

*Создание и правка задачи*
- При создании база сама ставит статус «Новая», автора и дату, а в истории сразу появляется запись «— → Новая». Передать эти
  поля в запросе нельзя: такой запрос получает отказ.
- Триггер правки следит только за названием, описанием, объектом и исполнителем, поэтому принятую задачу можно удалить.
  Сравнение учитывает пустые значения. Он запрещает правку принятых и снятие исполнителя не у «Новой».
- Роль назначаемого проверяется только при назначении и смене исполнителя, поэтому правка названия не падает, если
  исполнитель сменил роль.
- Триггеры создания и правки сначала проверяют роль и отвечают одинаково, чтобы ошибка не раскрывала чужие данные.

*Удаление*
- Идёт через два отдельных действия: для задачи и для объекта с задачами. Хранится, кто и когда удалил.
- Удаление объекта отмечает сначала сам объект, затем только живые задачи.
- Создание и перенос задачи блокируют целевой объект и только потом проверяют отметку, чтобы живая задача не осталась в
  удалённом объекте.
- Удалённую задачу нельзя двигать и править. Удалённый объект нельзя править, в нём нельзя создать задачу или перенести её
  туда.

*История*
- Прямая запись, правка и удаление закрыты для всех, кто обращается через API. Записи создаёт только база, она же ставит
  автора и время.
- Отдельный триггер запрещает изменение и удаление записей (Р14). Его может снять только владелец базы.

*Обязательные значения*
- Объект: название и адрес. Задача: название, объект, автор. Запись истории: кто. Описание необязательно, длина текста
  ограничена.
- Текст из любых пробельных символов считается пустым, в том числе перенос строки и табуляция.
- Задача не в статусе «Новая» обязана иметь исполнителя.
- Без текущего пользователя (например, в панели Supabase) база отказывает в создании задачи и смене исполнителя.

*Профили*
- Миграция создаёт профили и уже существующим пользователям. Без профиля доступа нет, сайт показывает «Нет доступа».

### 3.6. Стиль кода

- **Разделение:** экран и компонент показывают данные, хук хранит состояние запроса, `api.ts` обращается к базе. Бизнес-логика
  в компонентах не живёт.
- **Размер:** один файл решает одну задачу. Компонент примерно больше 150 строк делим. Это ориентир, а не жёсткий предел.
- **Типы:** строгий режим TypeScript, без `any`. Типы таблиц создаются по схеме базы.
- **Имена:** понятные и без сокращений, действия называем глаголами. Статусы в базе и коде на английском, русские названия
  только в `statuses.ts`.
- **Ошибки:** база возвращает код отказа, текст для пользователя лежит только в `shared/dbErrors.ts`.
- **SQL:** одна миграция на одну тему. Порядок в функциях: блокировка, проверка прав, проверка условий, действие.
- **Автопроверки:** ESLint и Prettier. Импорт в одну сторону и запросы только из `api.ts` проверяет встроенное правило ESLint
  `no-restricted-imports` (`eslint.config.js`). Внутри своего раздела импорт относительный, в остальном через `@/`.

### 3.7. Экраны

| Экран | Постановщик | Исполнитель |
|---|---|---|
| Вход | Email и пароль, после входа список объектов | Email и пароль, после входа «Мои задачи» |
| Список объектов | Все объекты, столбец «На проверке: N»; создать, изменить, удалить | Только объекты со своими задачами, без кнопок |
| Карточка объекта | Данные и все задачи: название, статус, исполнитель, задачи на проверке первыми; создать задачу | Данные и только свои задачи, без кнопок |
| Карточка задачи | Данные, история; изменить и удалить; принять или вернуть, когда задача на проверке | Данные, история; взять в работу или отправить на проверку, когда это доступно |
| «Мои задачи» | Нет | Свои задачи: название, объект, статус |

Общее для всех экранов:
- **Верхняя панель:** ссылки на разделы, имя и роль, кнопка выхода.
- **Формы:** создание и правка открываются в окне поверх экрана. На правке отправляются только изменённые поля, кнопка
  блокируется на время запроса.
- **Подтверждение:** при удалении объекта окно показывает число задач.
- **Отказ базы:** уведомление на русском. Если статус уже изменился, карточка сама обновляется.
- **Пустые списки:** простой текст, например «Задач пока нет».

Обратная связь на сетевые запросы (Р23):
- **Первая загрузка списка или карточки:** скелетоны по форме будущего содержимого.
- **Повторная загрузка данных:** старые данные остаются на экране, сверху небольшой индикатор.
- **Кнопка действия:** индикатор на нажатой кнопке, она и остальные действия этой карточки заблокированы до ответа. Это касается
  входа, выхода, смены статуса, удаления, создания и правки.
- **Формы:** поля и кнопки заблокированы на время запроса, окно нельзя закрыть до ответа.
- **Ошибка загрузки или нет сети:** понятное сообщение и кнопка «Повторить» на месте содержимого.
- **Устройство:** состояния показываются общими компонентами из `shared/ui`, а не пишутся заново на каждом экране.

### 3.8. Контракт базы и сайта

Единые имена для всех задач. Менять их можно только через основную сессию.

**Перечисления:** `app_role` — `manager` (постановщик), `executor` (исполнитель). `task_status` — `new` (Новая), `in_progress` (В
работе), `in_review` (На проверке), `accepted` (Принята), `rework` (На доработке).

**Таблицы схемы `public`**

| Таблица | Поля |
|---|---|
| `profiles` | `id` (uuid, ссылка на `auth.users`), `full_name`, `role` (по умолчанию `executor`) |
| `objects` | `id` (uuid), `name`, `address`, `created_at`, `deleted_at`, `deleted_by` |
| `tasks` | `id` (uuid), `title`, `description`, `object_id`, `assignee_id`, `status` (по умолчанию `new`), `author_id`, `created_at`, `deleted_at`, `deleted_by` |
| `task_history` | `id` (bigint, порядок записей), `task_id`, `actor_id`, `created_at`, `from_status`, `to_status`, `from_assignee_id`, `to_assignee_id`, `comment` |

- Все ссылки без каскадного удаления. Номера объектов и задач случайные (uuid).
- `task_history`: при создании `from_status` пуст, `to_status = new`, исполнитель заполнен, если назначен сразу. При смене статуса
  заполнены оба статуса. При смене исполнителя оба статуса пусты, а заполнены поля исполнителя (пустое значение означает «не
  назначен»).
- Длина текста: `name`, `title`, `full_name` до 200 знаков, `address` до 300, `description` до 5000, `comment` до 2000.
- Непустой текст содержит хотя бы один непробельный символ. Неразрывный пробел считается пробельным.

**Что доступно напрямую через API (`authenticated`)**

| Таблица | Чтение | Создание и правка |
|---|---|---|
| `profiles` | По Р10 | Нет |
| `objects` | По разделу 3.1 | Постановщик: `name`, `address` |
| `tasks` | По разделу 3.1 | Постановщик: `title`, `description`, `object_id`, `assignee_id` |
| `task_history` | По разделу 3.1 | Нет |

Удаления строк напрямую нет ни у кого. `anon` и `service_role` прав на эти таблицы не получают.

**Действия базы.** Сайт вызывает обёртки в `public` без повышенных прав, логика лежит в функциях с теми же именами в схеме
`private`. Вызвать их можно только после входа. Параметры: сначала номер, у остальных имена с префиксом `p_`.

| Действие | Параметры | Результат |
|---|---|---|
| `change_task_status` | `p_task_id`, `p_expected_status`, `p_new_status`, `p_comment` (необязательно) | Нет |
| `delete_task` | `p_task_id` | Нет |
| `delete_object` | `p_object_id` | Нет |

Служебные функции для правил доступа лежат в `private` и работают только с текущим пользователем: `current_user_role`, `is_manager`,
`is_executor`, `can_read_profile`, `can_read_task`, `has_task_in_object`.

**Коды отказов.** Функции и триггеры передают код в тексте ошибки (`message`), текст для пользователя есть только на сайте.

| Код | Текст на сайте |
|---|---|
| `task_not_found` | Задача не найдена |
| `object_not_found` | Объект не найден |
| `status_changed` | Статус уже изменён |
| `transition_forbidden` | Переход запрещён |
| `comment_required` | Укажите комментарий |
| `forbidden` | Недостаточно прав |
| `task_accepted` | Принятую задачу нельзя изменить |
| `assignee_required` | Нельзя снять исполнителя с задачи в работе |
| `assignee_not_executor` | Назначить можно только исполнителя |
| `history_immutable` | Историю нельзя изменить |

Коды из поля `code` на сайте тоже переводятся: `42501` — «Недостаточно прав», `23514` и `23502` — «Заполните обязательные поля»,
`invalid_credentials` (вход) — «Неверный email или пароль». Для неизвестной ошибки есть общий текст, для сбоя сети свой. Функции и
триггеры передают код чистым текстом, без префикса и пояснений: код засчитывается только при точном совпадении.

### 5.3. Общие правила для агентов

- Перед работой прочитать разделы 2, 3 и 4 этого документа и раздел 3.8 (контракт). Менять только свои файлы.
- Сначала тесты по сценариям задачи, затем код (`node:test`, Playwright только в З14). Комментарии и стиль — Р19 и раздел 3.6.
- Если спецификация не подходит или появился новый вопрос, остановиться и сообщить основной сессии. Молча не отступать.
- Локальную базу пересоздают только З3–З5. Остальные задачи только добавляют свои данные.
- Коммитит основная сессия после проверки результата. Статус задачи обновляет она же. Агенты не коммитят и не выкладывают.
- Секреты не выводить и не записывать. `claude.bat` не открывать. В npm и GitHub ходить с очищенными переменными прокси, `curl`
  к локальным адресам — с `--noproxy '*'`.
- В ответе: что сделано, чем проверено (команда и результат), что не проверено.

## 6. Открытые вопросы

**Блок 8**
- Какой публичный ключ у созданного проекта: `publishable` или `anon`.

**Подтвердить запуском на проекте**
- Гонки: смена исполнителя и статуса, создание задачи и удаление объекта, правка и принятие.
- Аккаунт без профиля против функций статуса и удаления.
- Какие права реально есть у ролей на проекте.
- Какой ролью работает редактор таблиц в панели, отвечает ли вход по-разному на существующий и несуществующий email.
- Регистрация прямым запросом, создание пользователя в панели, анонимный вход.

**Сверено с официальной документацией** (опытом не проверено)
- Пользователь может править `user_metadata`, но не `app_metadata`.
- Функции по умолчанию может вызвать кто угодно, функции с повышенными правами нельзя создавать в открытой схеме, для них
  нужен закреплённый `search_path` ([RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)).
- Представления по умолчанию обходят RLS (там же).
- Новые таблицы не получают права автоматически: новые проекты с 30 мая 2026, существующие с 30 октября 2026, в том числе
  `service_role` ([журнал изменений](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)).
- Токен живёт час по умолчанию, блокировка не отзывает выданный токен
  ([сессии](https://supabase.com/docs/guides/auth/sessions)).
- Сбой триггера на `auth.users` может мешать создавать пользователей
  ([управление пользователями](https://supabase.com/docs/guides/auth/managing-user-data)).
